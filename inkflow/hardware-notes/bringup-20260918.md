# Hardware bring-up — 2026-09-18

First session with the device actually attached. Everything here is measured on the
unit, not inferred. It corrects several earlier conclusions.

## The unit is NOT locked

An earlier diagnosis in this repo said it was. **That was wrong.** It rested on the
device not enumerating over USB — but at the time it was either not connected or not
powered. With it genuinely attached:

```
USB JTAG/serial debug unit
  Vendor ID:  0x303a (Espressif)
  Product ID: 0x1001
  Serial:     14:63:93:F6:82:4C
  Speed:      Up to 12 Mb/s
-> /dev/cu.usbmodem1101
```

esptool held a full conversation with it. A locked unit cannot do that.

## Chip and flash — matrix specs confirmed against hardware

```
Chip:       ESP32-C3 (Wi-Fi, BT 5 LE, Single Core, 160MHz)
Crystal:    40 MHz
USB mode:   USB-Serial/JTAG
MAC:        14:63:93:f6:82:4c
Flash size: 16 MB
Flash mfr:  0x85   device: 0x2018
```

The **flash manufacturer and device ID** were marked UNVERIFIED in the platform matrix
because no public teardown recorded them. Now measured.

## eFuses — three inferences replaced by facts

The matrix previously carried secure boot and flash encryption as *inferred* off from
behaviour, never confirmed. Confirmed now:

| eFuse | Value | Meaning |
|---|---|---|
| `SECURE_BOOT_EN` | **False** | Secure boot is off |
| `SPI_BOOT_CRYPT_CNT` | **Disable (0b000)** | Flash encryption is off |
| `DIS_USB_SERIAL_JTAG` | **Enable (0b0)** | USB-Serial/JTAG not disabled |
| `DIS_USB_JTAG` | False | USB-to-JTAG not disabled |
| `DIS_DOWNLOAD_MODE` | False | Download mode available |
| `DIS_PAD_JTAG` / `SOFT_DIS_JTAG` | False / 0 | JTAG not disabled |
| `DIS_FORCE_DOWNLOAD` | False | Forced download available |
| `WR_DIS` / `RD_DIS` | 0 / 0 | No eFuse write- or read-protection |

**Nothing is burned. The part is entirely open.**

This bears on an open community question. Secondary sources speculate that locked X4s
are locked by a burned eFuse; nobody had published a dump. On this unit **every
relevant eFuse is unburned**, so whatever "locking" means on affected units, it is not
an eFuse state this device shares. That does not disprove the eFuse theory for locked
units — it does show the theory is untested and that an unlocked unit looks completely
clean.

## Golden backup — taken

```
file:   x4-stock-golden-20260918T015022Z.bin
bytes:  16777216
sha256: 4e512a0b02b9bfa2451d998d553422644b4ca6c902e7391dc07fe84a3ef04bc2
```

Both `0x0` (bootloader) and `0x10000` (app) carry the `0xE9` ESP image magic, so the
dump is a real image rather than a failed read.

**It took 55 seconds, not the ~25 minutes the community guides claim.** Earlier docs in
this repo repeated that figure; it is wrong at 460800 baud over native USB.

The image is **not** in the repository — 16 MB of device-specific firmware does not
belong in git, and it is gitignored. It lives in `~/inkflow-backups/` and must be
copied somewhere durable by hand.

## The operational trap worth knowing

**The stock firmware does not keep USB-Serial/JTAG alive once it boots.**

Sequence observed: the device enumerated and esptool worked twice. The second command
ended with `Hard resetting via RTS pin`, and the device then vanished from USB
completely — not just the serial node, the whole device. It did not come back until a
full power-cycle and replug.

So the ROM bootloader presents USB on power-up, and the application firmware drops it.
Practical consequence:

**Always pass `--after no-reset`.** Any esptool command that ends in a hard reset boots
the stock app and takes USB away with it, costing a power-cycle. With `--after
no-reset` the chip stays in the bootloader and the connection survives — the backup and
the eFuse read above ran back-to-back on one connection because of it.

This is the most useful thing learned today and it is not documented anywhere found so
far.

## First custom firmware — running

`open-x4-epaper/sample-firmware` built and flashed to app0. Written with esptool
directly at `0x10000` rather than via `pio run -t upload`, so the bootloader, partition
table, nvs and spiffs were never touched. `Hash of data verified.`

On screen:

```
Xteink X4 Sample
Press Any Button
Power: Charging
Raw: 2811   Volts: 4.12 V   Charge: 98%
Top 5 Files on SD: .dropbox.device
```

Every subsystem the bench needs is confirmed working on hardware:

| Subsystem | Evidence |
|---|---|
| **EPD display** | Text rendering via GxEPD2 on `GDEQ0426T82` |
| **SD card** | Directory listing succeeded |
| **Battery ADC** | Raw 2811 → 4.12 V → 98% |
| **USB charge detect** | "Power: Charging" — GPIO20 reads high |
| **Buttons** | InputManager initialised, prompt displayed |

### Panel dimensions — conflict resolved

The feature survey logged a conflict: this project had 800×480 from Adafruit, while
`crossink-simulator`'s README gave 792×1040 portrait. **800×480 is correct.** The
working firmware drives `GxEPD2_426_GDEQ0426T82` and its own source comments it as
*"XteinkX4 has 4.26\" 800x480 display"*. Rendering works, so this is settled by a
working driver rather than by documentation.

### Pinout — confirmed in working code

```
EPD:  SCK=8  MOSI=10  CS=21  DC=4  RST=5  BUSY=6
SD:   CS=12  MISO=7
BAT:  GPIO0 (ADC)     USB-detect: GPIO20
```

Identical to the platform matrix. Those were read from a guide; they are now running.

### Battery ADC calibration point

`raw 2811 → 4.12 V` while charging. The bench needs battery sampling to estimate power
draw during sustained refresh, so this is the first real data point for that scale.

### Custom firmware keeps USB alive

Unlike stock, the sample firmware holds USB-Serial/JTAG up after boot — it builds with
`ARDUINO_USB_MODE=1` and `ARDUINO_USB_CDC_ON_BOOT=1`. **Flash cycles from here need no
power-cycle**, which makes iteration considerably faster than the stock-firmware dance.

### State of the device

The stock Xteink reader app is **overwritten**. Bootloader, partition table, nvs and
spiffs are intact, and the golden backup restores stock with a single
`write-flash 0x10000` (or a full-image write). Nothing here is one-way.
